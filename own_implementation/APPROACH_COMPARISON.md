# Comparison of the project-notes approach and teammate implementation

This comparison is for team discussion. It does not declare either approach final.

## Executive summary

The two approaches agree on the most important ideas:

- the source grain is one report for one unit in one filing;
- `unique_id` is the source-row key;
- the data does not provide a safe persistent physical-unit key;
- bedrooms and bathrooms require canonical mappings;
- rent and square footage are bands rather than exact measurements;
- utilities and occupancy history should not remain as repeating or multi-valued source fields;
- raw values and data-quality problems should remain auditable;
- foreign keys should connect the fact table to controlled lookup tables.

The largest difference is scope. The teammate’s `jun/house` implementation is a detailed, measured 21-table pipeline with a two-pass loader and round-trip validation. The current reference implementation is a smaller learning model that emphasizes understandable 3NF reasoning and Python preprocessing. It is not yet a replacement for the teammate’s complete loader.

## Ideas emphasized in your notes or in the current reference model

### 1. The initial property/unit decomposition is treated as an explicit hypothesis

Your notes proposed `Property`, `Unit`, and `SubmissionRecord`, then questioned whether `block_num` could actually identify a property. The revised approach makes that uncertainty central: `UnitReport` is the fact relation unless the source proves a stable property key.

The teammate also reached this conclusion, but the notes are useful because they show the design change from the first conceptual model rather than making the final model appear obvious from the beginning.

### 2. The model is intentionally kept understandable for course discussion

The current reference model uses fewer concepts than the teammate’s 21-table design. It is easier to explain in a mid-presentation, while the teammate’s model is stronger for a complete production-style load and audit.

### 3. Python preprocessing is separated from SQL DDL

The current approach places mappings in `clean_inventory.py` and leaves SQL focused on table creation and loading. The teammate’s pipeline also has Python cleaning, but it goes further by generating staging files and a complete `LOAD DATA` script.

### 4. No midpoint is generated by default

The teammate’s flat-file cleaner computes midpoint variables for analysis and uses assumptions for open-ended bands. The current reference approach stores boundaries and statuses without creating a midpoint. Both are defensible, but the midpoint should be labeled as an analysis assumption if the team uses it.

## Ideas emphasized by the teammate that the current reference model does not fully implement

### 1. Measured functional dependencies

The teammate measured dependencies such as:

```text
submission_year -> case_type_name
point -> neighborhood, district
monthly_rent -> rent bounds
square_footage -> square-footage bounds
```

The current reference documentation describes these as dependencies to test, but it does not contain the teammate’s full measured counts. Those counts should not be copied unless the same source export is used and the team reproduces them.

### 2. Duplicate filing groups

The teammate detects byte-identical rows and records duplicate groups without deleting them. The current reference model does not yet have a duplicate-group relation. This is a meaningful extension if duplicate analysis matters to the project.

### 3. Detailed date-unknown handling

The teammate separates valid dates, valid years, “Year Unknown” phrases, and malformed years. The current model has `occupancy_year` and `date_unknown_text`, but the implementation is simpler and still needs to be matched to the exact source export.

### 4. Full automated loading

The teammate’s `load_3nf.py` creates TSV files and a generated load script in foreign-key order. The current `preprocess.sql` is only a loading note. A final team implementation would need either a simplified loader or a clearly documented manual import sequence.

### 5. Broader utility vocabulary

The teammate models a larger controlled utility vocabulary and stores whether each utility came from a checkbox, free text, or both. The current cleaner has a smaller vocabulary and should be expanded only if the team decides the additional categories are useful and can be justified.

### 6. Contradiction checks

The teammate checks vacant units with rent, tenant units without rent, occupancy after signature, future dates, zero unit counts, reversed history ranges, and other contradictions. The current implementation checks only a subset. These are candidates for additional quality rules, not automatically required tables.

## Source-version difference

This is the most important comparison limitation. Your PDF notes and the teammate’s `jun/house` implementation describe an export containing fields such as `case_type_name`, `data_as_of`, and `data_loaded_at`, with occupancy history represented as JSON. The repository blob inspected earlier has a different 28-column header containing `location_id` and separate `occ_history_type`, `occ_history_start`, and `occ_history_end` fields.

Therefore, a difference between the two implementations may reflect a different source export rather than a disagreement about normalization. The team must choose one exact CSV and rerun the unique-value and functional-dependency analysis against it.

## How the music schema can guide the final SQL style

The attached music schema is useful as a formatting and explanation template, not as a design instruction. Its strongest conventions are:

- `DROP DATABASE`, `CREATE DATABASE`, and `USE` at the top;
- section comments before each table;
- comments explaining the source-field problem and the normalization decision;
- explicit primary keys, foreign keys, `UNIQUE` constraints, and nullable fields;
- comments explaining why a one-to-one table was split or why a many-to-many junction is needed;
- seed `INSERT` statements for controlled vocabularies;
- load-order comments explaining that parent rows must be inserted before child rows.

For the Rent Board project, comments can be based on the project notes, but the team should rewrite them in its own words. A useful table comment should answer:

1. What did the raw column or group represent?
2. What data-quality or normalization problem was found?
3. What relation stores the cleaned value?
4. Why does the chosen key and relationship make sense?
5. What limitation remains?

Example style:

```sql
-- BedroomLabel
-- The raw bedroom field contains spelling variants, numeric labels, studio
-- labels, and a small number of values that are not bedroom counts. The raw
-- label remains available for auditing while canonical_bedrooms supports
-- consistent grouping. Unparseable labels remain flagged rather than guessed.
CREATE TABLE BedroomLabel (...);
```
